# Kawaks 1.45 对照基准与 KOF 联机体验改进方案

**2026-10-27 / KOF-NET-PLAN-01**  
状态：工程决策与实验基线；KOF ROM/模拟器商业授权未取得。用户已在 Kawaks 1.45 最终中文典藏版中实测联机卡顿、常不同步，目标为明显优于该体验。本报告不宣称已在 Kawaks 与本平台之间进行同机同网络公平对照。

## 0. 重要前提

- Kawaks 1.45 官方 FAQ 确认其联机通过 Kaillera：https://www.kawaks.org/FAQ.htm
- GGPO 官方要求：同输入同状态、完整可保存恢复的游戏状态、每帧可单独模拟；不通过单纯 P2P 或下载速度替代：https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md
- MDN WebRTC DataChannel 的 unordered/unreliable 模式会放弃重传，maxRetransmits=0 不保证每个输入包送达：https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/createDataChannel
- 上游 Neon Fist 的成功仅代表**原创浏览器格斗原型**，并非已证明未经授权的 KOF 98 ROM、Kawaks 模拟器或街机版帧可按同样算法确定性回放。

## 1. 卡顿三类原因与正确修复

| 用户现象 | 可能原因 | 需要的措施 | 不应做什么 |
|---|---|---|---|
| 按键后半拍才出招 | 为等待远端输入而延迟本地模拟；渲染/输入管道额外延迟 | 回滚联网，预测远端输入，本地输入立即反馈；降低输入渲染管道时延 | 一味加带宽、换机房 |
| 画面偶尔跳动、卡住 | RTT/抖动、TURN 远端绕路、输入补发迟到、客户端掉帧 | 路由质量监测、短期输入预测、帧预算、区域 TURN 回退、有限缓冲 | 认为 1P/2P 自行直连就一定不卡 |
| 两边看到不同位置/胜负 | 丢失历史输入、随机数/状态未保存、延迟超出回滚窗口、不同游戏构建 | 确定性模拟、同帧状态哈希、ACK+请求补发、不可恢复时作废 | 让双方继续比赛并自动给用户天数 |

## 2. 采用的具体架构

**浏览器本地运行游戏** → 玩家本地帧时钟 60Hz 与独立渲染 → WebRTC 优先直连。对战包应是玩家输入，不要把游戏视频经美国 VPS 中转。平台服务器主要处理账户、房间、信令、赛程、战绩的审查记录。

网络建议两类消息分流：
1. **快速输入流**：小包、尽早发送、允许少量丢失、携带最近帧历史。优先极低延迟，不能让大块记录堵住正在进行的按键。
2. **可靠控制流**：协议/游戏版本握手、ACK 位图、缺帧请求、选择性补发、关键帧 hash、暂停/作废消息。可独立使用可靠 RTCDataChannel 并设置限流。

### 游戏模拟必须可回滚
- 每一个模拟帧确定性 60Hz，不靠渲染帧率推动物理模拟。
- 保存会影响结果的**全部状态**：双方位置/速度/连招、生命/气、判定盒、投射物、回合计时、命中停止、随机数种子、剩余时间及引擎内状态。
- 预测的对手输入与已经确认的真实输入分开储存；收到补回的历史输入后从最后可信快照重新模拟。
- 同帧并且在确认了所需输入后对比 hash；如果关键帧超出 rollback 窗口，不允许继续以可信游戏结果结算。
- 真实 KOF/NeoGeo 模拟需要**能保存完整内存/硬件相关状态并确定性恢复的模拟器**。GGPO 思路不能直接贴在旧 Kawaks 网络层上就得到现代体验。

### 网络质量管理
- 客户端先探测 local、srflx 和 relay 候选，记录真实候选对；优先低延迟直连。
- P2P 无法建立时才用就近 TURN，优先用户所在网络区域低 RTT 的中继；美国免费 VPS 适合轻量信令服务，但不应默认中转中国玩家操作输入。
- 在赛前测 RTT 中位数和 p95、抖动、丢包、浏览器 frame-time p95；从匹配开始标明连接质量。
- 根据网络实际预算设置输入延迟 0—2 帧、回滚窗口先试 6—8 帧；这些是**待实测起始参数**，不是固定万能值。RTT 和回滚的关系必须按同样单向/往返口径计算。
- 超出设备性能或网络下限时暂停/拒绝排位，不虚假宣传零延迟。

## 3. 本项目目前具有的、可核实的实际证据

- [P0-005](P0-005_TWO_PEER_RESULT.md)：两个独立 Chromium context 真实执行对战，P1/P2 双方都接收到远端输入；同帧哈希校验成立。
- [P0-006](P0-006_PACKET_LOSS_RECOVERY_2026-10-27.md)：原版丢一包出现哈希差异；4 帧输入冗余可恢复 1—4 连丢，但 5 连丢不能。
- [P0-008](P0-008_COMBINED_IMPAIRMENT_2026-10-27.md)：额外 90ms 每方向延迟 + 4 连丢，5 次重复中的桌面场景全部出现不一致。
- [P0-009](P0-009_RELIABLE_INPUT_PROTOCOL_DRAFT.md)：正式可靠输入 V2 协议方案。
- [V2 独立内核](../src/netcode/v2_protocol.mjs) 与 [可靠输入模块](../src/netcode/v2_reliability.mjs)：已写出协议编解码、ACK 窗口、缺失帧请求、有限历史重传、无法恢复时安全 ABORT 的**独立原型**。必须通过独立 GitHub Actions 单测并集成到真实游戏后才能用于上面的失败用例。不可因为“测试通过”就宣布实际格斗联机修好了。

## 4. 必须量化的 Kawaks 对照验收

在**相同两台设备、相同游戏内容和同一网络条件**下进行公平对照。Kawaks 1.45 作为当前用户体验基准；若另用 Neon Fist 等不同游戏，只能测通用技术能力，不可声称“同一款 KOF 已比 Kawaks 好”。

建议首先记录下列工程门槛（目标值可因真实网络调整）：

| 指标 | 初版拟定验收 | 注意 |
|---|---|---|
| 稳定渲染与模拟 | 游戏模拟固定 60Hz，桌面/手机各测 frame-time p50/p95 | 60FPS 不等于端到端输入延迟 0 |
| 无负载低 RTT | 本地按键不等待远端同步才响应；在网络发生抖动时不明显冻结 | 需高速相机/可信时间戳做实际输入至屏幕测量 |
| 双方状态一致 | 在无损、单包丢失、1/4/5/8 连丢及不同延迟场景逐帧做 hash 校验 | 任意一场“错误不同步但仍结算”不得通过 |
| 不可恢复的异常 | 必须拒绝可信赛果并保存安全脱敏证据 | 不要求网络不掉线，而要求错误可控 |
| 真实手机联网 | Windows↔Android、Windows↔iPhone、Android↔iPhone 各含不同 ISP / 5G 情况 | Chrome 移动模拟不能代表 Safari/安卓真机 |
| 相同人组 20 局以上 | 完局率、帧率、断线/作废比例、玩家主观手感、出招稳定性 | 不得仅凭一次短时 CI 报产品质量通过 |
