## 三、失败的第 3 轮：重要的非绿色证据

原始 CI job：`ten-repetitions (3)`，job ID `122822498868`，保留全部失败日志。

在 runner 中：
- HOST A 的首个本地非零操作为 `{handle:1, frame:109, mask:1}`，`armedAfterNonzero=true`，`dropped=5`，实际执行了发送延迟；
- GUEST B 确实采到 `{handle:0, frame:133, mask:8}`；共 15 次非零采集，但第一批捕获均停在 **frame 133**；
- 在两端 `move_cube_system` 的实际模拟输入记录中，`appliedByHandle[0]=0`，而 `appliedByHandle[1]` 分别达到 11、22；
- 双端仍运行至第 210 帧、记录的 Player 0 仍为初始 `x=12500,z=0`，没有表现出 Guest 已经按下的移动；Player 1 确实发生运动；
- 页面没有记录到 JS 运行时错误，资源问题仅为已独立验证可忽略的字体 `.ttf.meta`；因此 **不是简单地“网页没打开”或“浏览器完全没收到按键”**。
- 此日志支持的事实是“本地游戏采集的非零输入未进入实际模拟”；具体原因可能与 prediction-window 等包、输入帧时钟及 Chrome 调度时序有关，**尚未证明一定是 GGRS 库本身的 bug**。

**最关键的验收改进：** 如果仅比较双方同帧状态哈希，这一轮可能被错误判定为成功，因为双方都没有应用 Player 0 的输入。新增 Rust 的 `read_local_inputs` 与 `move_cube_system` 分立钩子，才真正捕捉到此失败。不能放宽这个条件。

## 四、计量局限

- 丢弃的是在非零输入捕获以后发生的 GGRS WebRTC 发送包；**尚未逐包解码证明 5 包全含对应非零输入帧**。不要把本实验说成精确丢了五帧按键。
- 每一轮是短时间、同一 CI 主机的两个 Chrome 进程。9/10 是这十次受控实验的通过数，**不代表真实玩家可靠率为 90%**。
- 原官方 Bevy 方块示例使用浮点 `f32` 运动状态，不覆盖格斗判定、手机设备、实际跨运营商 NAT/TURN、WASM 冷启动时延或 Kawaks 1.45 公平对照。
- 只冻结“9 PASS、1 FAIL”，不在补丁后的重跑中用绿灯覆盖第 3 轮旧记录。
- 另有 Rust 2024 `unsafe extern` 兼容写法更新版 CI [#40689765737](https://github.com/wpuu/kof/actions/runs/40689765737)，不得将此额外运行与上述 10 个样本混称同一版本的 20 次测试，结果需分别归档。

## 五、后续明确开发任务
