# P0-009 可靠双端输入协议 V2：可开发规格草案

日期：2026-10-27。状态：**仅完成方案设计，尚未开发或验证**。依据：[P0-008](P0-008_COMBINED_IMPAIRMENT_2026-10-27.md)。

## 目标
目前四帧冗余补丁可修复 1—4 连丢，却在 90ms 每方向额外延迟 + 4 连丢的 5 次桌面重复实验中全部发现同帧哈希不同。V2 要求：输入缺失时**可靠修正为同状态**；确实无法恢复时**及时标记为无效局并停止可信计分**。不能继续无提示分叉，也不能承诺物理零延迟。

## 输入帧协议与握手

1. 固定协议 Magic、版本 V2、消息类型、消息长度、最大帧号差；对非法数据立即拒绝，不允许稀疏数组因垃圾大帧索引被恶意扩容。
2. 每次对局生成随机 matchId，校验双方角色分配、游戏版本、配置 fingerprint。旧版 9B、实验 29B 和新版 V2 不可默默混连。
3. 类型候选：HELLO、INPUT、INPUT_ACK、RESEND_REQUEST、FRAME_HASH、MATCH_ABORT。
4. 每帧输入 mask 写入有界历史环形缓存，原型先取 256 帧；接收端维护连续 ACK 前沿与最近 32 帧已接收位图。
5. 发现缺口时精确请求缺失 frame；重发受到次数和速率上限约束。最近 4 帧捎带冗余可继续保留，但不能取代真正的确认与补发。
6. 回滚窗口之外的关键输入丢失不能静默忽略：暂停可认证比赛进度，有限次数恢复；不能恢复时 MATCH_ABORT 并使结果成为 VOID_UNVERIFIED。
7. 对相同模拟 frame、且输入已确认的历史状态比较 hash；不同步不得发放比赛奖励。哈希相同只代表模拟一致，不代表两位玩家没有串通。
8. WebRTC DTLS 不是游戏用户身份系统；账号身份、管理权限、安全审计和赛事裁判仍需独立设计。

## 指标与可靠性

现有 unrecoverablyLate 统计会把过期但相同的重复冗余输入也算进去。V2 应分开统计：
- duplicatedHistoryIgnored：收到相同内容的重复历史帧；
- historicalInputRepaired：历史输入确实被修正；
- criticalFramesTooLate：确实改变模拟、却已经无法回滚的 distinct frame；
- resendRequests、resendSuccess、ackGapCount、matchVoids；
- rollbackCount、rollbackDepth、confirmedThroughFrame、游戏帧时长 p95。

不得将原始 ICE/SDP、账号凭据或可识别用户数据写入公共仓库日志。

## Codex 开发拆分（按依赖顺序）

**V2-01：帧协议**。建立严格固定头和消息版本，添加长度、边界、恶意包、旧版本拒绝的测试。

**V2-02：ACK 与选择性补发**。实现历史输入有界缓存、ACK 位图、缺帧检测、请求、限速和补发测试。

**V2-03：可证实的一致性**。区分预测输入与已确认输入；不同步时先恢复，超出回滚范围则中止可信计分。

**V2-04：后端成绩审查**。确认同帧 hash、对局是否无效，以及可靠的成绩与争议记录；两端一致自报不能直接视为反作弊。

**V2-05：同一故障回归**。复用现有双端测试与 90ms＋4 包实验，扩展 5/8 连丢、抖动及随机丢包；通过标准为“状态一致或明确无效局”，不接受安静的数据分叉。

**V2-06：真实手机/异网**。Windows↔华为、Windows↔iPhone、华为↔iPhone，实际运营商与 TURN 情况分别记录。未使用真机不得宣称完成。
