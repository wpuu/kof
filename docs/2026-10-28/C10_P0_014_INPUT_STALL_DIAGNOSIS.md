# C10｜P0-014 输入采集后未及时进入模拟：真实浏览器延迟诊断

日期：2026-10-28（北京时间）。**真实执行并保留失败根因线索；尚未解决可玩性问题。**

## 1. 出发点：P0-013D 10 次实验中的真实失败

- [首轮十次 #40689108165](https://github.com/wpuu/kof/actions/runs/40689108165) 的 9 PASS / 1 FAIL，原始第 3 轮 `122822498868` 见 [C09](C09_P0_013D_10X_RESULTS.md)。
- 第 3 轮 Guest 在 GGRS 模拟 frame 133 多次采到玩家 `mask=8`（非零向右输入），但双方实际 `move_cube_system` 在后续记录中均未应用其 handle=0 输入；同帧状态虽相同，这名角色却没移动。
- 推论只到“输入采集与模拟应用之间存在可观测的等待/丢动作”，**并未证明是 GGRS 项目本体缺陷，而不是预测窗口、应用层按键读写时机、Chrome 调度或模拟故障叠加**。

- [诊断脚本](../../lab/matchbox_input_stall_diagnostic.mjs)
- [跨 run artifact 复用与三个用例工作流](../../.github/workflows/p0-014-input-stall.yml)
- 仍使用 90ms 人为每方向发送等待、±20ms 可复现抖动、HOST 非零键盘捕获后开始丢弃 5 个不可靠 GGRS DataChannel 发送包；
- 但这次按键在引擎真实 `move_cube_system` 应用其本地 handle 的非零输入之前持续保持，等待上限严格为 1.8 秒。记录同一浏览器 `performance.now()` 从第一非零捕获到第一非零实际模拟应用的时间；
- 双方仍要求真正移位、同帧量化状态一致、丢包计数实际等于 5、必需资源无错。

## 3. 三组真实结果

| 重复种子 | CI 结果 | Host 捕获→应用 | Guest 捕获→应用 | 观察到的单帧重复非零输入采集上限 |
|---|---|---:|---:|---|
| 1 | PASS | **212 ms** | 0 ms | Host 0，Guest 13 |
| 3（原先短按失败） | PASS | **796 ms** | 1 ms | Host 2，Guest 13 |
| 5 | PASS | **415 ms** | 4 ms | Host 13，Guest 20 |

含义：延长物理方向键按住直到引擎真正使用，本轮三个实验都最终收到了两个玩家的非零动作并在第 180 帧保持量化位置/速度一致；但是 **Host 本地操作响应到模拟应用出现高达 796ms 的等待**。

这是不符合精密格斗游戏手感期待的实验现象。不能把 3/3 绿灯宣传为“好打”“不卡”；反而证明必须区分**状态一致性**和**操作可用性/及时性**。

## 4. 下一步诊断／修复合同

**P0-014A：厘清“卡帧期间采集到输入却可能被覆盖”的准确路径。**

- 记录 `read_local_inputs` 收到非零输入的 frame/timestamp、实际提交给 GGRS 的 frame，`move_cube_system` 应用的 frame/timestamp，并以玩家 handle 区分。
- 把 GGRS `WaitRecommendation` / `NetworkInterrupted` / `DesyncDetected` 等相关事件、当前 frame、max prediction 与 input delay 记录成有界日志；不要泄露 ICE、SDP、用户真实 IP。
- 明确是哪一侧停帧、停多久、是本地模拟没推进还是输入进队列未被处理。没有根因前**不建议**简单把按键自动延长到 1.8s 作为产品修复。

**P0-014B：比较预测窗口与输入缓冲。**目前官方示例 `max_prediction_window=12`、`input_delay=2`。按一帧约 16.7ms，12 帧预测上限约 200ms；但“捕获到模拟应用”实际更长，所以先增加同步停帧指标，再分别测有界 16/20 帧候选对回滚 CPU、输入响应和游戏确定性的影响，避免失衡。

**P0-014C：最终质量门禁。**在用户实际网络场景之前，至少达到 90ms±20ms＋5 连丢下 10/10 双人真正输入模拟、同帧量化一致，记录每轮输入采集→应用的 p50/p95 和最大值，并明确可接受的交互阈值；不能通过放宽超时阈值挑绿灯。

## 5. 对最终商业目标的约束

- 同机 Chrome 短测仍不是 Android/iPhone Safari/跨运营商实测，更不是 Kawaks 1.45 同设备对照。
- 仅使用获许可的原创测试方块场景，无 SNK ROM、美术、原游戏音效、真钱/有价天数竞猜。
- GGRS＋Matchbox 目前仍作为优先网络研究候选，但被本轮发现的高本地输入等待**阻止直接宣称可以对公众提供好手感的格斗游戏平台**。

**本次收敛：成功分支 3/3 能在“等待直到应用”方式下操作一致，但 796ms 延迟是实际观察到的阻断，必须继续改进。**
